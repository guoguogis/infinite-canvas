# Pending Tests

The current release needs manual verification in these areas:

- heyroute video call script: the script is kept at `web/src/lib/heyroute-video-script.ts` and must be attached manually to each video model, with Base URL `https://heyroute.ai/v1`. heyroute is an OpenAI-compatible relay, but its video create endpoint takes **JSON** (`model`, `prompt`, `ratio`, `resolution`, `duration`) rather than the multipart form the built-in OpenAI path sends, so the built-in path cannot be used; polling (`GET {baseUrl}/videos/{task_id}`) and download (`GET {baseUrl}/videos/{task_id}/content`) do match. Polling runs every 15 seconds with a 30 minute timeout, matching the provider's own recommendation. Note that `seedance-2.0` and `seedance-2.0-fast` only accept `480p`/`720p` and only produce 15-second videos (any other duration is rejected with `invalid_request`), while `seedance-2.5` adds `1080p`. Reference images are not sent yet because the field names are unconfirmed, so image-to-video still needs verification.
- Aliyun happyhorse video call script: the script is kept at `web/src/lib/happyhorse-video-script.ts` and is needed because the protocol is DashScope native rather than OpenAI. Create posts `model` + `input.prompt` + `parameters.{resolution, ratio, duration}` to `{baseUrl-root}/api/v1/services/aigc/video-generation/video-synthesis` and **must** carry `X-DashScope-Async: enable` — without that header the route answers `403 AccessDenied: current user api does not support synchronous calls`. Polling gets `{baseUrl-root}/api/v1/tasks/{task_id}` until `output.video_url` appears, every 10 seconds with a 30 minute timeout. Note that `resolution` must be upper-case (`720P`) while the app stores `720p`, and that the image-to-video field is sent as `input.img_url` by convention but is unverified because only the text-to-video API was documented. A bare `{"model": "happyhorse-1.1-t2v"}` is accepted and returns a `task_id` before the body is validated, so failed probes still register a task that only fails at submission.
- Aliyun Wan image generation: `wan2.7-image` and `wan2.7-image-pro` use the DashScope native route `POST {baseUrl-root}/api/v1/services/aigc/multimodal-generation/generation` with `model` + `input.messages[].content[]` + `parameters.{size, n, watermark, thinking_mode}`, returning synchronously with the image under `output.choices[].message.content[].image`. This is a third distinct contract, so the script at `web/src/lib/wan-image-script.ts` is required. `size` may be either a preset or an explicit width/height, and the provider recommends presets; the app stores pixel strings, so the script splits the app's three tiers (0.79–1.74M, 2.36–4.19M, 6.33–8.29M pixels) at 2M and 5M. **The supported presets differ per model and per scenario**: `wan2.7-image` supports only `1K`/`2K`, and `wan2.7-image-pro` reaches `4K` only for text-to-image with no reference image, so the script caps the request at the model's highest supported preset. Content entries use `{ text }` and `{ image }`, and the provider documents 0–9 input images, so image-to-image is supported on the same route. The confirmed response is `output.choices[].message.content[].image` plus `usage` and `request_id`, which is what the script parses. Two behaviours worth knowing: `size` acts as a quality tier rather than an exact pixel size — requesting `2K` produced a `1488*704` image, not a square — and the API takes no ratio parameter, so the output aspect ratio is decided by the model from the prompt rather than by the app's size setting.
- 88api video call script: `web/src/lib/api88-video-script.ts` submits MiniMax video models through `POST {baseUrl}/chat/completions` with `model` + `messages` + `temperature`, then extracts the first `http` link from the reply text, because this relay (a new-api build, per its `X-New-Api-Version` header) does not use an upload-style `/videos` route. **The reply shape is unverified**: `minimax-h3-768p` currently answers `503 model_not_found: No available channel for model minimax-h3-768p under group auto (distributor)` even though it is listed by `GET /v1/models`, so the model needs an API key whose group actually routes it before this can be tested. The same key works for the Claude models, and `MiniMax-M3` fails with a server-side `model_price_error` (`tiered expr run failed: expr compile error: unrecognized character: U+005C`), which is a pricing-expression bug on the relay rather than a client problem.
- Empty default channels: a fresh profile must start with no providers and no models at all. The provider list should be empty rather than showing a generated OpenAI provider, every model picker should report that no model is configured, and generation should prompt the user to configure a provider instead of failing. Importing a configuration file must restore the providers, models, call scripts, and default model choices exactly as exported, and a profile that has been left empty must stay empty after a refresh.
- Provider Base URL versioning: the channel Base URL must be used exactly as entered, with no version segment appended anywhere. `https://api.openai.com/v1`, `https://generativelanguage.googleapis.com/v1beta`, `https://token-plan.cn-beijing.maas.aliyuncs.com/compatible-mode/v1`, `https://ark.cn-beijing.volces.com/api/v3`, and a Meta address such as `https://metaso.cn/api/minimax/v2` should all resolve correctly for built-in requests, Gemini requests, and call scripts. Omitting the version segment should send the request to the unversioned path rather than silently fixing it, and built-in image/video/audio/text templates plus the `http` and `request` helpers should join relative paths without adding a version.
- Meta video call script: the script is kept at `web/src/lib/metaso-video-script.ts` but is no longer attached to any default provider, so it must be pasted into a provider's model script when needed. It targets `POST {baseUrl}/video_generation` with `model`, a `content` array (`text` plus `image_url` entries), `resolution`, `duration` and `ratio`, then polls `GET {baseUrl}/query/video_generation/{task_id}` until the video address appears at `task.content.url`; the provider Base URL must itself end with `/v2`, because both routes return 404 without it. Resolution must snap to what each model accepts, and the allow-lists were measured per model rather than assumed: `MiniMax-H3` takes `480p`/`512p`/`768P`/`2K`, `seedance-2.0` takes `480p`/`720p`/`1080p`, and `seedance-2.0-mini` takes only `480p`/`720p` — sending a value outside the list returns `Seedance resolution 不支持` or `resolution 仅支持 …`. Provider error messages should surface instead of a generic failure, and polling runs every 4 seconds with a 15 minute timeout. **Reference image rules differ per model**: MiniMax-H3 accepts exactly one image and rejects a second with `输入媒体数量超过限制 (2013)`, while the seedance models accepted ten in probing and additionally require every image to carry a `role` at the same level as `type` and `image_url` — omitting it returns `Seedance image role 必须明确为 first_frame、last_frame 或 reference_image`. The script therefore sends only the first image for MiniMax-H3 and assigns `first_frame`/`last_frame` when the app is in first-and-last-frame mode with up to two images, otherwise `reference_image`. Every image must also be between 256 and 5760 pixels, and every model requires `duration` to be an integer between 4 and 15 (`Seedance duration 必须为 4 到 15 的整数，暂不支持自动时长`), which is narrower than the app's 4–30 second slider, so the script clamps the value to that range.
- Volcengine Ark Seedream call script: the script is kept at `web/src/lib/volcengine-seedream-script.ts` and, like the Meta script, must now be attached manually. It must map the requested pixel size onto the presets each model accepts (`1K`/`2K` for 5.0 Pro; `2K`/`3K`/`4K` for 5.0 and 5.0 Lite; `2K`/`4K` for 4.5; `1K`/`2K`/`4K` for 4.0), send `output_format` only for 5.0 Pro/Lite, and use `response_format: "url"` (result links expire after 24 hours, so they must be downloaded promptly). Text-to-image with `size: "2K"` against model `doubao-seedream-5-0-pro-260628` was verified returning one image; the other models and sizes still need checking. Provider failures must surface the real reason rather than a bare status code: Ark reports output-policy rejections as `400` with `error.code` such as `OutputImageSensitiveContentDetected.PolicyViolation` (the image was generated but flagged, typically for copyright), and reports sizes above the model's limit (for example `2880x2880` on a model capped at `2048x2048`) as `400` with an empty body.
- Aliyun Bailian exposes two API surfaces on the same host, and picking the wrong one is what makes these models look unavailable. `https://token-plan.cn-beijing.maas.aliyuncs.com/compatible-mode/v1` serves the OpenAI-compatible routes used by text and audio, while `https://token-plan.cn-beijing.maas.aliyuncs.com/api/v1/...` serves the DashScope-native routes used by `wan2.7-image`, `qwen-image-3.0-pro` and the `happyhorse-1.1-*` video models. Sending a native-only model to the compatible route returns a misleading `url error, please check url!` for images and `404 Model not exist.` for `POST /videos`, which does not mean the entitlement is missing. Because the app resolves the supported routes for text and audio, the call scripts strip a trailing `/compatible-mode/v1` from the Base URL before appending `/api/v1`, so one provider entry can host all of these models. Note also that `GET /compatible-mode/v1/models` is not authoritative — it lists 16 entries and omits every `happyhorse-1.1-*` model even though the native video route accepts them.
- Aliyun qwen image generation: `qwen-image-3.0-pro` must use the DashScope native route `POST {baseUrl-root}/api/v1/services/aigc/multimodal-generation/generation` with `model` + `input.messages[].content[]` + `parameters.{size, n, prompt_extend, watermark}`, returning `output.choices[].message.content[].image`. Sending it to the OpenAI-compatible `/compatible-mode/v1/images/generations` route answers `400 url error, please check url!` even though the model exists — the same signature the Wan models produce on that route, which means "this route does not serve this model" rather than a missing entitlement. **The `size` format differs per model on this one endpoint**: `qwen-image-3.0-pro` requires `'<width>*<height>'` with an asterisk and rejects both `1K`-style presets and the app's internal `1024x1024` form with `InvalidParameter: Expected format: '<width>*<height>'`, while `wan2.7-image` accepts presets such as `2K`. A `1024*1024` request was verified end to end returning one image in 44 seconds with `prompt_extend` and `watermark` accepted. The divider is protocol-specific and the provider calls this out explicitly: OpenAI-compatible mode uses `1024x1024` while DashScope native uses `1024*1024`. Image-to-image **is** supported by passing `image` (a URL, a Base64 data URL, or an array of 1–3 for the 3.0 series; null or an empty array returns 400), which the script sends as `{ image }` entries in the content array, so the earlier assumption that these models cannot edit was wrong. What is genuinely unsupported is the multipart `/images/edits` form, async calls, streaming, partial images and mask.
